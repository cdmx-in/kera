# Context management inside a run

A run that calls tools adds every result to the prompt, and a local model's window is small (Ollama starts at 4k to 32k tokens, depending on memory). This page describes what Kera does to keep a run inside the window, and how it recovers when a model call fails. A run on a small window shortens what it has read, step by step, instead of sending a prompt the server refuses. Every step is recorded in the [run trace](run-trace.md), so you can measure it.

## What happens, in order

1. **The loop knows the size.** After each model call it keeps the prompt size the server reported (`prompt_tokens`) and adds an estimate for the messages added since. Before the first report, after a rewrite, and when a server reports less than half of the estimate (some servers count only the uncached part), it uses the estimate alone. There is no tokenizer. The estimate is 3.3 characters per token until the server has reported a prompt of at least 1,000 tokens; from then on it uses the ratio of that report (the latest one), kept between 1.5 and 4 characters per token. Markdown, JSON and code run near 3 to 3.5, so the old fixed 4 ran about 16% low and every threshold below fired late.
2. **The loop knows the window.** In this order: the model parameter `context_window`, the parameter `num_ctx`, then a setting: `chat.context.window_local` (16,000) for a local model, `chat.compaction.threshold` (120,000) for a hosted one. Kera does not ask the server for a model's window, so unless one of the two parameters is set the window is that default, a guess. Set `context_window` in the preset's parameters (Workspace > Models) for any model whose real window you know; `num_ctx` is also sent to Ollama, so it sets the real window and Kera's belief in one place. When a call reports 97% or more of the window, the trace gets an `overflow_suspected` step: Ollama may cut the oldest messages of a prompt that is too long and still answer with success, so this is a sign that the window is smaller than assumed.
3. **Long results become files.** A tool result longer than `tools.spill_chars` (0 = one eighth of the window, at least 8,000 characters; -1 = never) is stored as a file of the user (`<tool>-result-<id>.txt`; lines over 500 characters are wrapped). The model gets the first 2,000 and last 1,000 characters and one line with the size, the file name and id, and the hint to read the rest with `view_file` or `grep_chat_files`. The file is an input of the step in the chat (shown on the step, never attached to the answer), joins the run's readable files, and in a saved chat is linked to the chat, so the next turn can list and read it. The file tools join a run whenever it has tools other than the core set, even without attachments. The results of the file tools themselves are never spilled (reading a spilled file back would spill again); they are limited by the next item instead. Spilled files stay when the chat is deleted (like tool uploads); remove them by `meta.source = "spill"` if storage matters.
4. **A round's results share the room.** When the model asks for several tools at once, the results of that round may together add what is left under 85% of the window (the rest is room for the reply and for the error of the estimate), counting the results of earlier rounds as room because the guard below can clear them again. The room is divided equally between the calls, at least 1,000 characters each. `view_file` and `grep_chat_files` are told their share: a page stops at it (never before one line) and says `[more: continue with start_line N]`, and a grep stops with a line saying how many matches fit and to narrow the pattern. Any other result more than 400 characters over its share (an MCP or OpenAPI tool, or the head and tail text of a spilled result) is cut and ends with `[Cut to fit the context window: N of M characters shown. Ask for the rest in smaller parts or with a narrower query.]`. Five to seven parallel `view_file` calls on a 16k window therefore read about 4,500 to 6,500 characters each instead of 30,000, and the model continues from the line it is told. On a large window the share is far above a normal result (about 300,000 characters when one call asks at a 120,000-token window). With `chat.context.enable` off nothing is limited.
5. **Old results are cleared.** Before a model call, when the size is over `chat.context.clear_at` (0.7) of the window, the content of tool results older than the newest `chat.context.keep_rounds` (4) rounds is replaced by one line (`[cleared to save context: <tool> returned N characters]`, plus the file name when the result was spilled), oldest first, until the size is down to `chat.context.clear_to` (0.5) or nothing older is left. It is one batch, so the prompt prefix changes rarely. A cleared result keeps its message: every tool call still has its result. The system prompt, earlier turns and the user's request are never touched.
6. **The run so far is summarised.** If the size is still over `clear_at`, and `chat.context.compact` is on, the run's own messages before the newest 2 rounds are condensed by the task model with the same summary prompt used between turns (plus a line asking to keep what was found, tried and still open, and to stay under a word limit). The notes are limited to one eighth of the window: the model is told the limit and the notes are cut to it when they run over, so a long summary cannot undo the room it made. The summary replaces the messages as one message, with the names of any spilled files. Cuts fall on round boundaries. If the summary call fails the run continues: the loop clears with only 2 rounds kept. There is no plan tool yet, so no plan message is carried over.
7. **Before every call, the prompt is made to fit.** Counting rounds protects nothing when a few rounds fill the window (one round can hold seven calls), so the last check before each model call works on tokens. When the size is over 85% of the window it (a) clears the results of every round but the newest, largest first, until it fits (the newest round is the one the model has not read yet); then (b) cuts the largest results, the newest round's too, to one common length (at least 500 characters) with the note above; then (c) summarises the run, unless step 6 just did, and cuts again. The system prompt, the earlier turns and the user's latest message are never touched. If the prompt is still over 95% of the window and the window is known (`context_window` or `num_ctx` is set), no call is made: the run ends with the error `context_length_exceeded` ("...more than the model's context window of N, and nothing more can be shortened. Use a model with a larger window, or shorten the message or the attached text"). With only the default window, a guess, the call is sent and the server decides; the trace says `too_large`.
8. **When the server refuses the prompt anyway.** Ollama answers a prompt over its window with HTTP 500 (`no user query found in messages`), OpenAI-style servers with 400 `context_length_exceeded`, a proxy may use 413. Sending the same prompt again fails the same way, so such an answer is not retried as it was: the loop takes the window to be a quarter smaller than its estimate of that prompt (the window is smaller than assumed, or the text counts higher), runs steps 5 to 7 with it, and sends the call once more. The smaller window stays for the rest of the run. If nothing can be shortened the run ends at once with `context_length_exceeded` (one call, not three). Other errors keep their retries.
9. **Between turns.** Compaction (`chat.compaction.enable`, now on by default) counts the system prompt, retrieved sources and tool definitions toward its threshold, and runs once the prompt and tools are built. The threshold is `compact_token_threshold` from the model parameters if set, else 70% of the window when the model declares one or is local, else `chat.compaction.threshold`. When `chat.context.digest` is on, an earlier assistant reply that used tools is sent with a short list of them (below).

## The digest of earlier steps

Earlier turns are replayed as text only, so a follow-up such as "use the second source" lost what the reply did. With the digest, an assistant turn that made tool calls ends with:

```
[Tool calls made for the reply above:
- search_web {"query":"rates"} -> first line of the result ...
- view_file {"file":"f"} -> failed: no such file]
```

- It is built from the message's stored steps, not from the database of tool results: the stored preview is already limited to 2,000 characters, and the digest keeps at most 150 characters of arguments and 300 of the result per step, on one line, for the newest 15 steps (it says how many earlier ones are left out).
- Arguments and results go through the guardrails' secret masking (private keys, cloud and API keys, tokens, bearer headers, `password: value` pairs, credentials in URLs). Personal data is not masked here; the guardrails policy (`guardrails.pii`) scans every assistant message sent to a model, digest included.
- For a model that is not local the digest lists tool names only (and "failed"): arguments and results of tools (mail, memory, internal documents) must not reach a hosted model that never saw them.
- Switch it off with `chat.context.digest`.

## Loop robustness

- **Retries.** A model call that fails before any event arrived (nothing shown, no side effect) is repeated up to `chat.model_retries` (2) times, after 1 s and 2 s, when the error is 429, 5xx, a connection error or the idle timeout. A failure after the first event is never retried: the text is already shown. A prompt the server says is too long is not repeated unchanged, even when it answers with a 500 (item 8 above). Each try is a trace step; a repeated one has `will_retry` and the next has `attempt`.
- **Round cap.** At `chat.max_tool_iterations` (30; `cowork.max_tool_iterations`, 100, for tasks) the model gets one more call without tools and with a line asking for the final report, so a task ends with a report instead of a status line. That step has stop reason `round_cap` and `final_report` in the trace. If that call fails the run still ends normally.
- **Repeat guard.** The same tool with the same arguments `chat.repeat_limit` (3) times in a row is not run the third time; the result says so and asks for another approach. `0` turns it off.
- **Task web budget.** A task has `cowork.web.max_searches` and `cowork.web.max_fetches` (15 each) per run; a chat reply keeps `web.search.max_calls_per_turn` and `web.fetch.max_calls_per_turn` (3).
- **Parallel calls.** The calls of one round run together (at most 4 at once) only when there are several and every one belongs to the web, knowledge or files built-in sets; results keep the call order. Any other tool in the round keeps the whole round serial. `chat.parallel_tools` switches it off.

## Settings

| Key | Default | Meaning |
|---|---|---|
| `chat.context.enable` | `true` | Size tracking, clearing and mid-run summaries (spilling and the other items below have their own switch). |
| `chat.context.window_local` | `16000` | Window assumed for a local model without `context_window` or `num_ctx`. |
| `chat.context.clear_at` / `clear_to` | `0.7` / `0.5` | Start and stop of a clearing batch, as a share of the window. |
| `chat.context.keep_rounds` | `4` | Newest rounds whose results are not cleared by the 70% rule; the 85% check above clears them too, largest first, when they alone fill the window. |
| `chat.context.compact` | `true` | Summarise the run when clearing is not enough. |
| `tools.spill_chars` | `0` | Spill results longer than this (0 = automatic, -1 = never). |
| `chat.context.digest` | `true` | Digest of earlier steps on earlier assistant turns. |
| `chat.compaction.enable` | `true` | Between-turn compaction (was `false`). |
| `chat.model_retries` | `2` | Extra tries of a failed model call. |
| `chat.repeat_limit` | `3` | Identical calls in a row before one is refused (0 = off). |
| `chat.parallel_tools` | `true` | Run read-only calls of a round together. |
| `cowork.web.max_searches` / `max_fetches` | `15` / `15` | Web budget of one task run. |

All are in Admin > Settings > Chat (and Web for the task budget). Model parameters: `context_window` (tokens), `num_ctx`, `compact_token_threshold`.

Fixed values, not settings: the 85% target and 95% limit of the pre-call check, the share of a window one summary may take (one eighth), the 1,000-character least share of a result, the 3.3 characters per token before the first report.

## What the trace shows

Steps of kind `compaction` (name in the Admin > Traces list): `clear` (results cleared, tokens before and after; `scope` is `old` for the 70% rule and `recent` for the 85% check), `truncate` (results cut, the length they were cut to, tokens before and after), `summarise_run` (messages summarised, tokens before and after, characters of the notes; error `compaction_failed` when it fell back to clearing), `spill` (tool, characters, file id), `overflow_suspected` (reported prompt tokens, window), `too_large` (nothing left to shorten: tokens, window; error `context_length_exceeded` when the run ended there, `sent` when only an assumed window was over) and `overflow_retry` (the server refused a prompt: HTTP status, tokens and window before and after; error `nothing_to_shrink` or `context_length_exceeded` when no retry followed). Tool steps carry `spilled`, `repeat_refused`, `capped` (the result was cut to its share, which is `cap_chars`; `truncated` is set too) and `result_chars` (the size before the cut); model steps carry `attempt`, `will_retry` and, for the closing call, `final_report` with finish `round_cap`; a refused prompt has the error `context_length_exceeded` and the HTTP status. Window and its source (`context_window`, `num_ctx`, `setting`, or `server` after a refusal) are on the `clear`, `truncate` and `summarise_run` steps. No text is stored.

Questions to ask in SQL: how often a run needed clearing (`name = 'clear'`), how often the server refused a prompt (`name = 'overflow_retry'`), how often a result was cut to its share (`detail->>'capped'`), the largest prompt per round (`prompt_tokens` of model steps) before and after switching `chat.context.enable`, how many model calls were retried (`detail->>'will_retry'`), how many tasks ended at the cap (`finish = 'round_cap'`).
