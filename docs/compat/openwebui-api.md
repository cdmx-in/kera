# Open WebUI compatibility contract

Kera serves a subset of the Open WebUI HTTP API so existing scripts and clients keep working after migrating. This document is written from observed request and response shapes, in our own words. Implement compatibility routes from this file, never from Open WebUI source code (see CONTRIBUTING.md).

Status legend: **planned**, **done**.

## Authentication

Every route accepts `Authorization: Bearer <token>` where the token is either a session token or a personal API key starting with `sk-`. Browser sessions also send the `kera_session` cookie; a POST/PUT/PATCH/DELETE authenticated only by that cookie is accepted from the same origin only (CSRF), so scripts should use the header. Errors use `{"detail": "<message>"}` with the HTTP status.

## OpenAI-compatible

| Route | Status | Notes |
|---|---|---|
| `GET /api/models` | done | Also `GET /api/v1/models` and `GET /v1/models`. `{"data": [model...]}`. Each model has `id`, `name`, `object: "model"`, `created`, `owned_by` (`ollama` or `openai`), `connection_type` (`local` or `external`), `local`, `hidden`, `kind` (`chat`, `embedding` or `rerank`; Kera addition), `features` (enabled feature ids), `defaultFeatures`, `toolIds` (`server:<id>`, `builtin:<name>`), `suggestionPrompts`, `profileImageUrl`, `capabilities`, and `info: {id, base_model_id, name, meta: {description, capabilities, hidden, suggestion_prompts, knowledge, toolIds, builtinTools, profile_image_url}, params}`. Only models the caller may use. Hidden models are listed for API-key callers and with `?include_hidden=true`. Embedding and rerank models (from Ollama `/api/show` capabilities, LiteLLM `/model/info` mode, else `embed`/`rerank` in the name) are left out unless `?kinds=all`, and a chat with one fails with `model_not_chat`. Ordered by the `site.model_order` setting, then name. |
| `POST /api/chat/completions` | done | Also `/api/v1/chat/completions` and `/v1/chat/completions`. OpenAI request body (`model`, `messages` with string or `text`/`image_url` content, `stream`, generation options, `tools`). Extensions: `chat_id`, `id` (assistant message id), `parent_id`, `user_message: {id, parentId, content, files}` (the web app's new turn), `files: [{type: "file"\|"collection", id}]`, `features: {web_search, code_interpreter, memory}` (absent = the model's defaults), `tool_ids` (`server:<id>` or bare ids; absent = the model's servers), `temporary`, `stream_format: "events"`. On a chat with `mode: "cowork"` (Kera addition) the run adds the cowork prompt (setting `cowork.prompt`, built-in when empty) right after the preset prompt, caps tool rounds at `cowork.max_tool_iterations` (default 100) instead of `chat.max_tool_iterations`, and waits up to 12 h for an `ask_user`/`confirm` answer (30 min otherwise); a caller without `features.cowork` gets `403 forbidden`. There is no request field for it: the chat's mode decides. The model preset's prompt (with variables), parameters (request values win), knowledge, tools and hooks apply for every caller, with or without `chat_id`; the server runs the tool loop and returns the final answer. When the body carries `tools`, only those are offered and tool calls are returned to the caller (`finish_reason: "tool_calls"`). `stream: false` -> `{id, object: "chat.completion", choices: [{message: {role, content, reasoning_content?, tool_calls?}, finish_reason}], usage, sources (nested citations), kera: {run_id, message_id, chat_id, tool_calls, sources, files, parts}}`; content is the text of the last model round. `stream: true` -> `chat.completion.chunk` events (`delta.content`, `delta.reasoning_content`, final `tool_calls` for passthrough, a usage chunk, `data: [DONE]`); progress rides along as chunks with `choices: []` and `kera: {type, data}`. `stream_format: "events"` -> the native dialect (see below). Errors before the run: `{detail, code, error: {message, code}}` with the HTTP status (`404 model_not_found`, `409 local_lock`, `409 busy`). A run continues when the client disconnects. |
| `GET /api/v1/chats/{id}/messages/{mid}/stream?after=<seq>` | done | Kera extension: re-attach to a running answer (also `Last-Event-ID`). `after=0` starts with one `snapshot` of the state so far. A finished or lost run answers a `snapshot` of the stored message and `done`. Temporary chats use the `temp:<id>` chat id from the first event. |
| `POST /api/v1/chats/{id}/messages/{mid}/cancel` | done | stops the run; the message is kept with status `stopped`. |
| `POST /api/v1/chats/{id}/messages/{mid}/calls/{callId}` | done | `{value}` answers an `ask_user` (`[{question, answers[]}]`) or `confirm` (`true`/`false`); 404 when already answered. Owner only. |
| `GET /api/v1/chats/{id}/runs` | done | `[{run_id, message_id, model, seq, done, created_at}]` of live and recent (10 min) runs. |
| `POST /api/v1/runs/{run}/events`, `POST /api/v1/runs/{run}/ask`, `POST /api/v1/runs/{run}/files` | done | callbacks for tool and hook servers, `Authorization: Bearer <run token>` (15 min, from `X-Kera-Callback-Token` / the hook envelope). `events`: `{type: status\|sources\|files\|block, data}`. `ask`: `{kind: confirm\|choice\|input, title, message, questions?, timeout_ms}` long-polls up to 240 s -> `{answer}` or `{answer: null, reason}` (`timeout`, `disconnected`, `run_ended`, or `unattended`: a scheduled run has nobody to answer, so it returns at once; do not ask again). `POST /api/v1/runs/{run}/files?name=<file name>` (same token): the raw body becomes a file of the run's user, typed by `Content-Type`, capped by `files.max_mb` (413 above) and at 500 files per run (429 above), not linked to the chat, meta `{source: "tool", run_id, chat_id, message_id}` -> `{id, name}`; return the id in a result's `images` or `files`. |

Native event dialect (`text/event-stream`, `id:` = seq, `: ping` every 15 s, `X-Accel-Buffering: no`): every `data:` is JSON with `type`, `seq` (1, 2, ... per message) and `messageId` (plus `chatId` on the first event of a temporary run). Types: `delta {text}`, `reasoning {text}` / `{done, durationMs}`, `tool_call {callId, name, server, args}`, `tool_result {callId, status: ok\|error, preview, files?}`, `status {description, done, id?, action?, hidden?, query?, urls?, count?, callId?}`, `sources {sources: [{id, name, title, url, fileId, page, snippet, score}]}`, `files {files: [{id, name, size, contentType, type}]}`, `block {block}`, `snapshot {parts, files, sources, status, pendingCalls}`, `ask_user {callId, questions}`, `confirm {callId, title, message}`, `compaction {state, summary?, before?, after?}`, `title {title}`, `follow_ups {follow_ups}`, `usage {usage}`, `error {code, message}`, `done {status?: "stopped"}`.

## Files and knowledge

| Route | Status | Notes |
|---|---|---|
| `POST /api/v1/files/` | done | multipart field `file`, optional `metadata` (JSON, stored as `meta.data`). Returns `{id, user_id, hash, filename, meta: {name, content_type, size}, data: {status: "pending"}, created_at, updated_at}` (epoch seconds). `?process=false` stores without extraction (status `completed`). Over the size limit (`files.max_mb`, default 100) -> 413. |
| `GET /api/v1/files/` | done | the caller's files, newest first; admins may add `?all=true`. |
| `GET /api/v1/files/{id}` | done | same object; `data.status` moves `pending` -> `processing` -> `completed` or `failed` (`data.error`). Clients poll this. Files the caller cannot read answer 404. |
| `GET /api/v1/files/{id}/process/status` | done | `{status}`. |
| `GET /api/v1/files/{id}/content` | done | raw bytes with Range support. Inline for images, PDF and plain text, otherwise attachment; `?attachment=true` forces download. `Content-Disposition` carries `filename` plus RFC 6266 `filename*`. HTML, SVG and XML are always attachments with `Content-Security-Policy: sandbox`; `X-Content-Type-Options: nosniff` always. Session cookie or bearer. |
| `GET /api/v1/files/{id}/content/{name}` | done | same as `/content`; the name is ignored. |
| `GET /api/v1/files/{id}/data/content` | done | `{content: <extracted text>}`. |
| `GET /api/v1/files/{id}/preview?sheet=n` | done | Kera extension: `{kind: csv\|xlsx\|text\|pdf\|image\|docx\|other, sheets, sheet, rows: string[][], truncated}`, capped at 2,000 rows x 200 columns (text: first 200 KB, one column per line). |
| `DELETE /api/v1/files/{id}` | done | owner or admin; removes the stored blob. `{message}`. |
| `GET /api/v1/knowledge/` | done | `{items: [...], total}`: collections the caller can read (owner, admin or a read/write grant), newest first. Each item: `{id, user_id, name, description, meta, created_at, updated_at, write_access, embedding_model: {id, connection, model, dim} \| null, fts_config, reindexing, status: {files, chunks, pending, processing, completed, failed}}`. |
| `POST /api/v1/knowledge/create` | done | `{name, description}` (other fields such as `access_control` are ignored; new collections are private). Needs `workspace.knowledge`. Returns the collection. |
| `GET /api/v1/knowledge/{id}` | done | the collection plus `files` (the `/files` items). 404 when the caller cannot read it. |
| `GET /api/v1/knowledge/{id}/files` | done | `{items: [{id, user_id, filename, meta, size, chunks, data: {status, file_status, error?}, created_at, updated_at}], total}`. `data.status` is the indexing state (`pending` -> `processing` -> `completed` or `failed`); `file_status` is the extraction state. |
| `POST /api/v1/knowledge/{id}/file/add` | done | `{file_id}`; a file still being extracted is indexed when extraction completes. Adding a file again re-queues it only when it failed. Needs write access to the collection and read access to the file. Returns the collection with `files`. |
| `POST /api/v1/knowledge/{id}/file/remove` | done | `{file_id}`; drops the link and its chunks, the file itself stays (delete it with `DELETE /api/v1/files/{id}`). |
| `POST /api/v1/knowledge/{id}/file/update` | done | `{file_id}`; indexes the file again. |
| `POST /api/v1/knowledge/{id}/update` | done | `{name?, description?}`. |
| `DELETE /api/v1/knowledge/{id}/delete` | done | removes the collection, its chunks and grants; returns `true`. |
| `POST /api/v1/knowledge/{id}/reindex?embedding_model=&connection=` | done | Kera extension: re-embeds every file. With `embedding_model` the collection moves to that model (on `connection`, default `rag.embedding.connection`); the old chunks answer queries until every file is done; moving to another model (or naming a `connection`) is admin-only (403). Without `embedding_model` a move in progress is cancelled. `{status: true, queued}`. |
| `GET/PUT /api/v1/knowledge/{id}/grants` | done | Kera extension: the collection's grants `[{principal, permission, managed}]` (`user:<id>`, `user:*`, `group:<id>`; read or write). PUT replaces them; owner, admins and write-grant holders. |
| `POST /api/v1/retrieval/query/collection` | done | `{collection_names, query, k, k_reranker?}` (ids or names) -> `{documents: [[text...]], metadatas: [[{name, source, file_id, knowledge_id, page?, headers?}]], distances: [[score...]]}`, one inner list, best first. Hybrid vector + full-text search fused by weighted reciprocal rank, then the reranker when `rag.reranker.url` is set; scores are reranker relevance (0-1) or fusion scores. `k_reranker`, else `k`, else `rag.top_k_rerank` results. Also served at `/query/collections`. |
| `GET /api/v1/retrieval/embedding` | done | `{embedding_engine, embedding_model, embedding_batch_size}` (engine = connection id). |

## Chats, models, users, feedback

| Route | Status | Notes |
|---|---|---|
| `POST /api/v1/chats/new` | done | ChatForm `{chat: {title, models, tags, history: {currentId, messages: {id: {id, parentId, role, content, model, timestamp, done}}}}, folder_id?}`; the messages are stored (an assistant entry with `done: false` waits for a completion with that `id`). Returns the chat object. The client's chat id is ignored. Kera addition: `chat.mode` is `chat` (default) or `cowork` (a task; needs `features.cowork`, else 403); other values -> `400 bad_mode`. The mode never changes afterwards. |
| `GET /api/v1/chats/{id}` | done | `{id, user_id, title, folder_id, share_id, archived, pinned, created_at, updated_at, tags, meta: {tags}, mode (chat\|cowork; Kera addition), chat: {id, title, models, tags, history: {currentId, messages: {id: {id, parentId, childrenIds, role, content, model, timestamp, createdAt (ms), done, status, error?, files, sources, statusHistory, usage, followUps, parts, pendingCalls, seq?}}}, messages: [active branch]}}`. A streaming message carries the live state and `seq` (resume from it). Imported tool traces and nested citations are rendered in the web app's shape. |
| `POST /api/v1/chats/{id}` | done | `{chat: {title?, pinned?, history: {currentId}?}}`; returns the chat. |
| `DELETE /api/v1/chats/{id}` | done | `true`; needs `chat.delete`. |
| `GET /api/v1/chats/?page=n` | done | also `/chats/list`: `[{id, title, updated_at, created_at, pinned, archived, folder_id}]`, newest first, 60 per page (no page = all), archived left out; `?folder_id=`, `?tag=`. Cowork tasks are left out of this and every other chat list, including `GET /chats/all/tags`. |
| `GET /api/v1/chats/pinned`, `/archived`, `/folder/{id}`, `/search?text=&page=` | done | same list shape. Search matches every word as a prefix in titles and message text; `tag:<name>` words filter by tag. |
| `POST /api/v1/chats/{id}/pin`, `/archive` | done | toggle; return the list entry. `GET /chats/{id}/pinned` -> bool. |
| `POST /api/v1/chats/{id}/folder` | done | `{folder_id}` (null = top level). |
| `POST /api/v1/chats/{id}/share`, `DELETE ...` | done | snapshot of the chat now -> `{id, share_id, chat_id, title}` (sharing again refreshes the snapshot); `GET /api/v1/chats/share/{share_id}` returns it in the chat shape to any signed-in user (`/s/<share_id>`). |
| `GET/POST/DELETE /api/v1/chats/{id}/tags`, `DELETE .../tags/all`, `GET /chats/all/tags`, `POST /chats/tags` | done | tags `{name}` are lower-case with `_` for spaces; lists are `[{id, name, user_id}]`; `POST /chats/tags {name}` lists chats with that tag. |
| `POST /api/v1/chats/{id}/messages/{mid}`, `DELETE ...` | done | `{content}` edits a message; delete removes it and its replies (the active leaf moves to its parent). Both return the chat. |
| `GET/POST /api/v1/folders/`, `GET/DELETE /folders/{id}`, `POST /folders/{id}/update`, `/update/parent`, `/update/expanded` | done | `{id, user_id, parent_id, name, is_expanded, created_at, updated_at}`; deleting a folder keeps its chats at the top level. |
| `GET /api/v1/cowork` | done | Kera addition, needs `features.cowork`: the caller's cowork tasks `[{id, title, status: running\|needs_input\|done\|stopped\|error, model, files, created_at, updated_at}]`, newest first, archived left out, at most 200. `status` comes from the current message (`needs_input` = streaming with a pending question; no answer yet = `running` for 2 minutes after the last change, then `stopped`); `model` is that message's model, else the chat's last model; `files` counts distinct files on assistant messages. |
| `GET/POST /api/v1/cowork/schedules`, `PUT/DELETE /api/v1/cowork/schedules/{id}`, `POST /api/v1/cowork/schedules/{id}/run` | done | Kera addition, scheduled Cowork tasks; needs `features.cowork_schedule` (off by default, admins always) and `features.cowork`. A task is `{id, title, prompt, model_id, tool_ids, features (null = the assistant's defaults), files, frequency: hourly\|daily\|weekdays\|weekly, at_minute (minutes after local midnight; hourly: minute of the hour), weekday (weekly, 0 = Sunday), timezone (IANA), enabled, notes, next_run_at, last_run_at, last_chat_id, last_status: ""\|running\|done\|stopped\|error, last_error}` (times in epoch seconds). `tool_ids`, `features` and `files` are what `POST /api/chat/completions` would take for the same task; on save `tool_ids` keeps only the tool servers that work for the caller today. `PUT` takes any subset of the fields; changing `model_id` clears `notes`. `GET ?all=1` (admins) lists every user's tasks with `owner` and without `prompt`, `notes` and `files`. `POST .../run` starts one run now -> `{chat_id}` (`409 running` / `409 at_capacity`). Limits: settings `cowork.schedule.max_per_user` (5, `409 limit`), `cowork.schedule.max_concurrent` (2; 0 pauses every schedule) and `cowork.schedule.max_minutes` (120, then the run is stopped). At each due time the server starts an ordinary `mode: "cowork"` chat as the owner (`meta.scheduled_task`), with `ask_user` and every tool question refused at once and the run failing with `tool_unavailable` when a requested tool server cannot join (not connected, expired, local-only on a hosted model). Each run is told the task's saved notes and the previous run's closing report (same assistant only) and may replace the notes with the `save_task_notes` tool. A slot missed while the server was down runs once; a task never overlaps itself. |
| `POST /api/v1/pipelines/{name}/runs`, `POST .../runs/{run}/steps`, `POST .../runs/{run}/sync`, `PUT .../runs/{run}/files`, `POST .../runs/{run}/finish`, `GET .../runs/{run}`, `GET /api/v1/pipelines/{name}/health` | done | Kera addition, pipelines (see `docs/pipelines.md`): outside scripts keep knowledge collections equal to a folder and report their steps and logs. Authenticated only by the pipeline's own token, `Authorization: Bearer kp-...` (40 characters after the prefix, stored as a SHA-256, shown once); the token must belong to `{name}` (else `401`), a switched-off pipeline answers `403 pipeline_disabled`, and no user session or API key works here (nor a `kp-` token anywhere else). `runs`: `{trigger?: script\|push, steps?: [name], dry_run?}` -> `201 {run, url, version, dry_run, collections: [{id, name}]}`, `409 run_active {run, trigger, started_at, active_at}` while one is open. `steps`: `{steps: [{name, status?: pending\|running\|ok\|warning\|failed\|skipped, error?, counts?, log?}]}` applied in order, at most 1 MiB (`413`) and 100 steps per run -> `{ok, ignored}`; an empty list is a heartbeat; a closed step only moves to a worse status; logs and errors are masked for secrets and stripped of control characters, each log line gets the server's UTC time (256 KiB kept per step, 4 MiB per run, errors 2,000 characters). `sync`: `{collection (a target's id or unambiguous name), files: [{name, sha256, size}] (at most 20,000; a name is one file name of at most 200 bytes), complete}` -> `{upload, unchanged, received, adopted, ambiguous, stale, refused?}`; `403 not_a_target` for any other collection (the API never creates one), `409 reindexing` while the collection changes embedding model. `files?collection=&name=&sha256=`: the raw bytes of one file, `400 checksum_mismatch`, `413` above `files.max_mb`; the file is staged beside the old version and swapped in when indexed. `finish`: `{error?}`. `GET runs/{run}`: `{id, pipeline, trigger, dry_run, status: running\|ok\|warning\|failed, client_done, error, started_at, active_at, finished_at, counts, steps: [{seq, kera, key, name, status, started_at, finished_at, error, counts, log_dropped}]}` (steps without logs; reading also settles the run). `health`: `200` or `503 {status: ok\|warning\|never_run\|failed\|late, detail, last_ok_at}`, needs the token. |
| `GET/POST /api/v1/admin/pipelines`, `GET/PUT/DELETE /api/v1/admin/pipelines/{name}`, `POST .../{name}/token`, `POST .../{name}/once`, `GET .../{name}/runs[?before=&limit=]`, `GET .../{name}/runs/{run}`, `GET .../{name}/runs/{run}/steps/{seq}`, `POST .../{name}/runs/{run}/close` | done | Kera addition, admin, pipelines. A pipeline is `{id, name, title, owner: {id, name, email}, targets: [{id, name, missing}], every_minutes, token_prefix, adopt, allow_mass_delete, enabled, managed, created_at, updated_at, late, running, last_ok_at, last_run}`. `POST` `{name (1-40 lowercase letters, digits, dashes), title?, targets?: [collection id or exact name], new_collections?: [name], every_minutes?, enabled?}` -> `201 {pipeline, token}` (the only time the token is shown; the creating admin owns the pipeline and the new collections; two targets may not share a name, `400 duplicate_target_name`). `PUT` any of `title, owner_id, targets, new_collections, every_minutes, enabled` (a new owner takes over the pipeline's files and the target collections the old owner held, in one transaction; the name never changes). `DELETE` keeps the collections and their files (they go back to origin `kera`) and drops staged versions. `token` -> `{token, token_prefix}`. `once`: `{adopt?, mass_delete?}` sets the one-shot flags (adopt same-named files that no pipeline owns; allow a refused removal), cleared by the next ok or warning run. `runs` -> `{runs: [run without steps], more}`; a run's `counts` add up its collection steps. `steps/{seq}` is a step with its `log`. `close` fails a stuck run (a running script step fails, steps that never started are skipped, nothing is removed). A user who owns a pipeline cannot be deleted (`409 pipeline_owner`). |
| `GET /api/v1/desktop/{chat}` | done | Kera addition: `{active}`, whether the chat has a running desktop on the desktop sidecar (asks the sidecar's `GET /sessions/{chat}/view` with `X-Kera-User-Id: <caller>`, since sidecar sessions are keyed by user and chat; never starts one). 404 for a chat the caller does not own and while the `desktop.url` setting is empty (the web hides the panel). |

| `GET /api/v1/desktop/{chat}/websockify` | done | Kera addition: the live view's websocket only. | Route | Status | Notes |

| `GET /oauth/{provider}/login?next=` | done | redirect to the provider (PKCE S256, state in an encrypted 10-minute cookie). `next` must be a same-origin path, else `/`. |

| `POST /api/v1/auths/signin` | done | public; JSON `{email, password}` (any other content type: `415`). Needs password sign-in on (else `403 password_disabled`). Answers like `GET /api/v1/auths/` plus `{token, token_type, expires_at}` and sets the same `kera_session` cookie as the OAuth callback. Every failure (unknown email, wrong password, no password, disabled or pending user, empty or oversized input) is the same `401 invalid_credentials` "Invalid email or password". Tries are counted per email and client address together (lock from the 5th try), per email across all addresses (from the 30th) and per address across all emails (from the 20th): a lock starts at 30 s, doubles with each further try up to 15 min and answers `429 rate_limited` with `Retry-After` (seconds) and `retry_after`. | `POST /api/v1/auths/update/password` | done | signed-in session (an API key gets `403 session_required`); `{password, new_password}` (the current password and the new one; at least 10 characters and at most 1024 bytes, not the email address, not a very common password, a repeated character or a plain run, not just `kera` or the email name with digits). Answers `{status: true, token, token_type, expires_at}` and sets a fresh cookie: every other session of the user stops working, this one continues with the new token (Open WebUI answers a bare `true`). Wrong current password: `400` with `field: "password"`, counted like a sign-in try; `400 no_password` for an account without one; `403 password_disabled` while password sign-in is off. |

## Tool servers and per-user OAuth

| Route | Status | Notes |
|---|---|---|
| `GET /api/v1/tools/` | done | `[{id, name, kind: "openapi" \| "mcp" \| "builtin", description, authenticated, auth_type: "none" \| "bearer" \| "header" \| "user_oauth", provider?, auto_enable?, connected_at?, functions: [names], error?}]`: the tool servers the caller may read (admins: all enabled ones) plus the built-in tool sets. `authenticated` is true unless the server needs the caller's own OAuth grant and the caller has not connected it; `connected_at` (epoch seconds) is set when they have. `functions` honours the server's name filter and disabled list; a server that cannot be reached within 8 s lists none and sets `error`. |
| `GET /oauth/clients/{provider}/authorize?next=` | done | Kera extension, browser only. Needs a session (otherwise redirects to `/auth?redirect=...`). Redirects to the provider with PKCE S256 and the provider's scopes; Google also gets `access_type=offline` and `prompt=consent` (so a refresh token is issued). The redirect URI is `<KERA_URL>/oauth/clients/{provider}/callback`. State, verifier, user and `next` travel in an encrypted 10-minute cookie. |
| `GET /oauth/clients/{provider}/callback` | done | exchanges the code, stores the token encrypted per user and provider, redirects to `next` (a same-origin path) or `/?tools=<tool server id>`. Failures redirect with `?oauth_error=<code>` (`invalid_state`, `session_mismatch`, `provider_denied`, `unknown_provider`, `exchange_failed`, `server_error`). |
| `DELETE /api/v1/oauth/clients/{provider}/session` | done | revokes the grant at the provider (RFC 7009: refresh token, else access token) and deletes it; `{ok: true}`, also when nothing was connected or the provider row is gone. A 4xx from the provider (token already invalid, or a revocation that can never succeed) still deletes it. When the provider answers 5xx or is unreachable the grant is kept and the answer is 409 `{detail, code: "revoke_failed"}` (never 5xx, which a CDN may rewrite). |

Tool calls carry `X-Kera-User-Id`, `X-Kera-User-Email`, `X-Kera-Chat-Id`, `X-Kera-Message-Id`, `X-Kera-Files` (comma-separated file ids), `X-Kera-Callback` and `X-Kera-Callback-Token` headers (OpenAPI and MCP alike), plus `Authorization: Bearer` with the server's key or the user's OAuth access token (refreshed when it expires within 5 minutes; a refresh the provider rejects deletes the grant). A `user_oauth` server may also set `auth.header` + `auth.key`: that header carries a static service key next to the user's token. `X-Kera-Callback` is `<KERA_CALLBACK_URL or KERA_URL>/api/v1/runs/<run>`; set `KERA_CALLBACK_URL` to an internal address when the public URL sits behind a proxy that cuts long requests (the `ask` long-poll lasts up to 240 s). An OpenAPI result that is a JSON object with `content` gives the model only `content` and the chat its `parts` (UI blocks), `files` and `sources`; anything else goes to the model as is. `images` (file ids, e.g. screenshots uploaded through the `files` callback) are shown on the tool step, not attached to the answer, and a model with `capabilities.vision: true` (set explicitly; a model without the capability does not get tool images) sees the round's last PNG, JPEG, GIF or WebP image of at most 20 MB in one user message after the round's tool results (the last 3 such messages are kept, older ones are blanked). Otherwise the tool message gets a note such as "(image not shown: this model has no vision)" or "(image not shown: image/svg+xml is not a supported image type)". Known limitation: some providers (Mistral's API, vLLM in `mistral` tokenizer mode) reject a user message right after tool messages, so a run with tool images fails there; leave `capabilities.vision` unset for such models. MCP `image` content parts are saved as files and also passed as `images`. Results longer than the server's `max_result_chars` (default setting `tools.max_result_chars`) are cut with a note. MCP servers are spoken to over Streamable HTTP, protocol revisions 2024-11-05 to 2025-11-25 (initialize, sessions, SSE responses, elicitation in form mode, progress and log notifications).
