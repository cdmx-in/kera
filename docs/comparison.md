Rows left out because every project in the table does the same: retrieval over uploaded files, MCP tool servers, OIDC sign-in, code execution. The differences that matter in practice:

- **Footprint.** Open WebUI and AnythingLLM are one container and start with less than Kera does. Kera asks for Postgres and gets a multi-user database from the first start, with no Redis, vector database or queue added later. LibreChat and Onyx run several services.
- **Licence.** Kera is Apache-2.0 without a branding clause or tenant limits. Open WebUI's licence allows more than 50 users to run it as is, but not to change its branding without permission.
- **In the base install.** Guardrails with an audit trail, per-user spend through LiteLLM, knowledge Pipelines with a flow view, and configuration as code (`kera apply`, `kera export`).
- **Where Kera is behind.** The ecosystem and community are much smaller, there is no desktop or mobile app, the interface is not translated, and sign-in is email and password, Google or OIDC only (no LDAP, SAML or SCIM). If those matter more than the points above, one of the other projects is the better choice.

Dify and LobeHub are broader application platforms. They are not in the table because several cells could not be verified. Mattermost has an AI plugin (Agents), which is a different kind of product (a chat platform with an assistant) and is not compared here.

## Durability: a run that a restart interrupts

Checked on 2026-11-27 against each project's own current documentation. These are different kinds of product from each other and mostly from the chats above: [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence) is a library, Agent Server is the server LangChain offers to run its graphs, OpenClaw runs agents behind its Gateway and n8n is a workflow tool. The table compares one thing only. Kera's side, with its limits, is in [durable-runs.md](durable-runs.md).

| | Kera | LangGraph library | LangGraph Agent Server | OpenClaw | n8n |
|---|---|---|---|---|---|
| What holds the state | Postgres, which Kera needs anyway | Your application's checkpointer. In-memory ones lose everything on restart; the docs recommend a persistent one such as Postgres for production | Postgres. It also needs Redis, which holds only short-lived data | The Gateway's SQLite database for conversations and transcripts | n8n's database. Queue mode needs Redis as well |
| After the process dies in mid-run | The next Kera process takes the run over and goes on from the last checkpoint | The docs have your code call the graph again with the same thread id (`invoke(None, config)`), which loads the latest checkpoint and retries unfinished work | A sweeper puts runs whose heartbeat has lapsed back in the queue; an interrupted run can resume from its last checkpoint | At start-up the Gateway sends an interrupted session a new input that asks the agent to check the current state and continue. It does not replay the old execution, and some orphaned runs are not resumed | The execution is marked `crashed`. We found no page that says n8n continues it by itself. The "Save execution progress" setting lets a workflow resume from where it stopped after an error |
| A step that may already have taken effect | Read-only calls are made again. A call in flight that may have changed something is not; the model is told the outcome is unknown | In a failed super-step, nodes that had completed are not run again. A node that runs again starts from its beginning, so side effects should be idempotent | Not checked separately | An unfinished tool call is not replayed; the agent is asked to check before repeating work | On a retry after a failed node, that node processes all its input again, including items it had handled. The docs say to check the target app first |
| Waiting for a person | Stored in Postgres: 30 minutes in a chat, 12 hours in a task, no setting for either | An interrupt waits indefinitely (it needs a checkpointer) | Not checked separately | An unfinished tool approval is not replayed after a restart | The Wait node resumes after an interval, at a set time, on a webhook call or on a form submission. From 65 seconds it moves the execution to the database. A time limit for it can be switched on or off |
| Replay or fork from an earlier step | No | Yes: replay from a past checkpoint, or fork it with changed state | Not checked | Not checked | Not checked |
| More than one instance | Not a supported setup yet; live token streaming does not cross instances | Not checked | API servers and queue workers scale independently, and any instance can take a cancel or stream request | Not checked | Queue mode adds workers. Several main processes need the self-hosted Enterprise plan |

Where the others are ahead:

- **LangGraph** can go back: replay from an earlier checkpoint or fork it. Kera keeps only the latest checkpoint of a run and deletes it when the run ends. An interrupt in LangGraph has no time limit in its docs, while Kera's questions time out. And as a library it lets you design the steps yourself; Kera resumes its own chats and tasks, nothing else.
- **Agent Server** and **n8n** are built to scale across several processes. Kera does not support that yet.
- **n8n** can wait for an outside event, such as a webhook call or a form. Across a restart, the only thing a Kera run can wait for is an answer to its own question.
- **OpenClaw** keeps its sessions in SQLite, so there is no database server to run. Kera needs Postgres.
